# 类人化 与 本地权限

> 两个问题：怎么让它在聊天里不像机器人；接到 QQ 后它的本机权限和原生 agent 是否一致。

---

# 一、本地权限：和原生 agent 一样吗

## 结论

**能力完全一样，差异只在"审批界面"和"有没有人看着"。**

权限不是由"从 QQ 进来"决定的，而是由 **agent 进程以哪个 OS 用户、在哪个目录、用什么 permission mode 运行** 决定的。

| 维度 | 原生（IDE/终端里跑） | 经 QQ 跑（ACP bridge spawn） |
|---|---|---|
| 进程身份 | 你的用户 | 同一个用户（bridge 以什么身份跑就是什么身份） |
| 文件读写 | 整个用户可访问范围 | **完全一样**，没有额外沙箱 |
| 执行 shell | 一样 | **完全一样** |
| 工具集 | 你配置的 MCP / 内置工具 | 一样（ACP 会话初始化时由 bridge 把 MCP 列表下发给 agent） |
| 审批方式 | 编辑器弹框，点允许 | `session/request_permission` 转成 QQ 消息，你回 y/n |
| 审批强度 | 你在屏幕前，能看到 diff | **默认更容易被一路放行**（远程、嫌麻烦、群聊里分不清） |

所以真正的问题不是"权限降不降级"，而是：**人不在旁边时，它替你做决定的风险变高了。**
最容易犯的错是 bridge 里图省事写成 `always allow`——那比原生 agent **更宽松**，等于把安全阀拆了。

## 审批链路（ACP）

```
agent 想执行 rm -rf build/
   │ session/request_permission
   ▼
bridge 判定（渠道/用户/命令风险）
   ├─ 私聊 + 你本人 + 非高危 → 发"要执行 X，回 y 确认" → 等你回复 → 回传 allow/deny
   ├─ 群聊/公开渠道 → 直接 deny（不给任何工具权限）
   └─ 120s 无响应 → deny（默认拒绝，不是默认允许）
```

三条铁律：

1. **默认拒绝**。超时、渠道不明确、用户不在白名单 → 全部 deny
2. **公开渠道零工具权限**。群聊/弹幕/评论里只允许纯对话，绝不 spawn 有 shell 的 agent
3. **高危命令二次确认**。`rm -rf`、`format`、`shutdown`、`git push -f`、写系统目录 → 强制单独确认，不给"始终允许"

## 三种权限姿态（选一个）

### A. 等同原生（最省事，最危险）

bridge 用你自己的账号跑，工作目录就是家目录。能力 = 你在终端里能做的所有事。
适合：单人私聊、机器就是你的开发机、能接受"手机丢了等于电脑丢了"。

### B. 收窄（推荐）

- 专用系统用户：`useradd -m fishbot`，只给它需要的工作目录权限
- agent 只允许在该目录内活动（`cwd=/srv/workspace`），系统盘只读或不可见
- agent 自身的 permission mode 设严格（多数 CLI agent 支持 `--permission-mode` / allowed tools 白名单）
- 只挂载必要的 MCP，不给数据库/云凭证
- 效果：能干活，但删不到你的照片、推不了你的仓库

### C. 沙箱（最稳，折腾）

容器内跑 agent，只 bind mount 一个工作目录，无 `--privileged`、无 docker socket。
非 root 用户、`no-new-privileges`、只读根文件系统 + tmpfs。

**Windows 上要注意**：
- 用普通用户跑服务（任务计划/nssm 别选 SYSTEM，SYSTEM 权限过大且不可控）
- UAC 提权不会自动继承，但你也别用管理员身份启动 bridge
- 想隔离就用独立本地账户 + 目录 ACL，或 Docker Desktop 容器

## 一个必须知道的坑

多数 CLI agent 在**非交互（无 TTY）**环境下，遇到需要审批的操作会直接失败或走默认策略，而不是停下来等人。
所以 ACP bridge **必须实现 `request_permission` 回调并真的等待**，否则你会看到大量"权限被拒"或"工具调用失败"，而误以为是 bug。

# 二、类人化：把它从"客服口吻"拽回"人"

## 先定原则

类人 ≠ 假装是人。公开渠道（B站/群聊）要遵守平台规则，不伪装真人身份；类人指的是**节奏、语气、分寸**，不是身份欺骗。

## 六个可工程化的点

### 1. 节奏（最容易出戏的地方）

机器人特征：秒回、一次吐一大段、条条带列表。
人的特征：有思考间隙、话分段、长短不一。

```python
def typing_delay(text: str) -> float:

    base = len(text) / 5
    return min(0.6 + base * 0.35, 4.0) + random.uniform(0, 0.8)

def split_like_human(text: str) -> list[str]:
    # 按"意思块"切，不是按长度硬切；单块 1~3 句
    ...
```

三个具体规则：
- **短问短答，不要凑字数**。"在吗" → "在"，不要回三段
- **超过 3 行才分段**，段间 0.6~1.5s；短答案一次发完
- **别秒回**。复杂问题先"嗯，我看下"再给结果；简单问题 1~2s 内给

### 2. 取消机械 ack

之前架构里写的"收到，处理中…"是工程思维，出戏。
改成：
- 预计 5 秒内能答 → 不 ack，直接答
- 预计更久 → "我查下" / "稍等，这个要看下" / 只发一个"…"（真的，很有效）
- 长任务中途 → "还在弄，马上"

**永远不要每条都回"收到"**。第二次出现就露馅了。

### 3. 去 AI 味（后处理 + prompt 双管）

后处理能兜底的低级特征：

```python
BAN = ["首先", "其次", "最后，", "综上所述", "总之", "希望对你有所帮助",
       "作为一个AI", "根据您的问题", "需要注意的是", "总的来说"]

def de_ai(text: str) -> str:
    for w in BAN:
        text = text.replace(w, "")
    text = re.sub(r"^\s*\d+[.、]\s*", "", text, flags=re.M)   # 干掉自动编号
    text = re.sub(r"\n{3,}", "\n\n", text)
    return text.strip()
```

prompt 侧写死：
- 不用列表，除非用户要"步骤/清单"
- 一句话能说清就一句话
- 不重复用户的问题
- 不解释自己要做什么，直接做
- 允许口语、允许说"不知道"

### 4. 分场景人格（三套 prompt）

| 场景 | 语气 | 长度 | 主动 |
|---|---|---|---|
| 私聊 | 像熟人，可以吐槽、可以有情绪 | 随意 | 可主动提醒 |
| 群聊（被 @） | 简洁、有分寸、不抢戏 | 短 | 不主动插话 |
| 公开渠道（B站/弹幕） | 极简、克制、不辩论 | 极短 | 不主动 |

文件放 `config/prompts/private.md`、`group.md`、`public.md`，Router 按 `InboundEvent` 选。

### 5. 记忆要"记得住人"，不是"记得住上下文"

纯对话历史显得呆。有效的三类记忆：
- **人**：称呼、偏好、在做什么项目、明确说过不喜欢的东西
- **事**：上次没做完的任务、答应过的事
- **时间**：早/晚、周末、上次聊天隔了多久（隔三天再回"好的"就很假）

实现很轻：`profile` 表存 JSON，每次拼 prompt 时带上前 5 条事实；`/记 xxx` 手动加，重要对话自动抽取。

### 6. 群聊的分寸（最像人的部分其实是"不说话"）

- 只被 @ 或明确点名才回
- 不参与别人的争论，不在别人对话中间插话
- 连续被人追问才多说一句，不要越回越长
- 不懂就说"这个我不确定"，比硬答更像人

## 一句话回答你的两个问题

- **权限**：和原生 agent 一模一样，因为是同一个进程同一个用户；不一样的只有审批框变成了聊天消息，而**这恰恰是风险点**——所以默认拒绝、公开渠道零权限、高危二次确认，三条必须写进代码，不能靠自觉。
- **类人**：不靠模型变聪明，靠四件事——**节奏（延迟与分段）、沉默（别每条都 ack）、去 AI 味（后处理兜底）、分寸（群里少说话）**。
